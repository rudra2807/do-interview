# Architecture & Spec Decisions

A running log of the meaningful design/architecture decisions made on this project, with brief rationale. Routine implementation steps aren't logged here, only genuine forks where more than one reasonable approach existed.

- **DB access via Prisma**, not raw `pg` or a query builder like Knex. Schema-first, type-safe client, built-in migrations: fastest path to correct CRUD + evaluation logic with the least boilerplate.
  Consequences: adds a build-time dependency on the Prisma CLI and generated client for every build; schema changes are written and reviewed as generated SQL migrations rather than inferred automatically.

- **Assume an external/self-managed Postgres instance**, no `docker-compose.yml` committed. The app only ever consumes a `DATABASE_URL`; local dev points it at whatever Postgres the developer runs themselves. CI provisions its own throwaway Postgres via a `services:` block directly in the GitHub Actions workflow, so this doesn't block automated testing.
  Consequences: a new contributor must have their own Postgres running and their own databases created before anything works locally; there is no single command that stands up the whole stack.

- **Per-user overrides are in scope**, not an addition beyond spec: the assignment explicitly requires enabling/disabling "for a specific user," distinct from the global default. Override always wins over the global default when one exists.
  Consequences: doubles the write and invalidation surface compared to a global-only flag: every write path (flag update, flag delete, override set, override delete) needs its own cache invalidation rule, tested separately.

- **Folder structure: strict layering.** Routes/controllers are thin HTTP adapters only; all business logic lives in a services layer; repositories are the only layer that talks to Prisma; validation schemas (zod) are kept separate from the Prisma persistence schema.
  Consequences: more files and indirection than a smaller service would need; a single new operation typically touches a route, a controller, a service, and a repository rather than one file.

- **Hard delete for flags** (cascades to overrides), not soft-delete/archive. No audit-history or evaluation-log requirement exists in the spec, so this avoids unrequested scope; noted as a stated tradeoff in the README rather than a gap.
  Consequences: deleting a flag is not recoverable, and there is no record of what the flag or its overrides were once it is gone.

- **Deployment target: DigitalOcean App Platform**, deployed early (before the rest of the feature work) specifically to validate the build, health-check, and rollout pipeline while the app was still just the scaffold plus `/health`, so deployment issues surface before there's a larger surface area to debug.
  Consequences: later infrastructure changes (the PRE_DEPLOY job, connection_limit) had to be retrofitted onto an app that was already live, each requiring an explicit spec update and redeploy rather than being part of a single initial setup.

- **Database on App Platform: the Dev Database tier**, not a standalone Managed Database cluster. Cheaper and faster to stand up for what is currently a scaffold; upgradeable later to a full Managed Database with no app code change, since the app only ever sees a `DATABASE_URL`.
  Consequences: no standby, limited backups, and an unpublished connection limit, all acceptable for this project but not something to run real production traffic against as is.

- **App Platform config as code**: the app is defined by a committed `.do/app.yaml` and created via `doctl apps create --spec .do/app.yaml`, not clicked together in the DO web console. Reviewable and reproducible, consistent with the project's "production-ready" bar.
  Consequences: `deploy_on_push` alone redeploys using the app's currently stored spec, not whatever is in the repo; every spec change needs an explicit `doctl apps update` as a separate step, which is easy to forget.

- **Pinned Prisma to 6.19.3, not the `latest`-tagged 8.0.0-rc.15.** `npm install prisma@latest` currently resolves to a release candidate (DigitalOcean's registry has it tagged `latest` ahead of a stable release), and Prisma 7 made a breaking change removing `datasource.url` from `schema.prisma` in favor of a separate `prisma.config.ts` plus driver adapter. That's meaningful extra complexity/novelty for a take-home a reviewer will read, so we use the latest *stable* line (6.x) with the conventional schema-url and `migrate dev` workflow instead.
  Consequences: misses whatever Prisma 7 actually improves, and this pin will need a deliberate, reviewed upgrade later rather than happening automatically.

- **Evaluate endpoint contract fixed to a specific shape**: query param `user_id` (not `userId`), response `{flag, user_id, enabled, reason}` with `reason` one of `"user_override" | "global"`. This was specified directly rather than left to design; other endpoints built before this contract existed (the override PUT/DELETE responses) were later unified to the same snake_case convention for `user_id` and `updated_at` to avoid a client-facing inconsistency, but the base flag resource shape (create/list/patch responses) stays camelCase, mirroring the Prisma model directly. Unifying that too would be a larger, unrelated change to already-tested endpoints, not something this decision covers.
  Consequences: the API now has two casing conventions live at once, snake_case on evaluate/override responses and camelCase on the base flag resource, which a client integrating against this API has to know about.

- **All request schemas use zod's `.strict()`**, rejecting unknown/misspelled fields with 400 instead of silently stripping them. Found via testing that a typo like `defaultEnable` instead of `defaultEnabled` was silently ignored, creating a flag with the wrong default and no error at all. Strict rejection trades some forward-compatibility (a client sending extra metadata fields would now get a 400) for catching this class of client bug immediately.
  Consequences: a client sending any extra field, even a harmless or forward-compatible one, gets a 400 instead of having it ignored.

- **Override create-vs-update status (201 vs 200) is determined by attempting `create()` first and falling back to `update()` only on a real Prisma P2002**, not by comparing the row's `createdAt`/`updatedAt` timestamps. The timestamp approach was tried first and proven unreliable under true concurrency: two requests issued in the same millisecond can both see equal timestamps on the same row (Prisma computes them client-side per call), which could tell the loser of a race it had created a row it only updated. The create-then-fallback approach is deterministic because it relies on Postgres's unique constraint, not on timing.
  Consequences: every override update costs an extra round trip (a failed create, then an update) compared to a single upsert statement.

- **Evaluation caching is cache-aside with invalidate-on-write and a 30 second TTL backstop**, implemented with `lru-cache` and a per-flag epoch counter, wired through the composition root in `src/container.ts`. Only computed evaluation results are cached, keyed by flag and user. A flag-level write evicts every cached user for that flag without touching other flags; an override write evicts only that one user's entry for that flag. The epoch guard exists because a slow, already-in-flight read can otherwise resolve after a concurrent write and cache a stale value; concurrent cold reads for the same flag and user are also coalesced (singleflight) so N simultaneous misses cost one repository call, not N, with the singleflight key itself scoped by epoch so a request arriving after an invalidation never coalesces onto a slower read that started before it.
  Consequences: correctly evicting exactly the right cached entries per flag, and only per flag, took meaningfully more implementation and testing effort than a simpler approach that cleared the entire cache on any write would have needed.

- **Epoch counters are monotonic and are never deleted, not even when a flag is permanently deleted.** This looks like an unbounded leak but is intentional: deleting an epoch entry resets it back to the default of 0, which could collide with a slow in-flight read that captured epoch 0 before any write had ever happened to that flag, letting it cache a stale result for a flag that no longer exists. Growth is bounded by the number of distinct flag keys ever created over the process's lifetime, not by request volume, so the memory cost is negligible.
  Consequences: epoch state accumulates for the lifetime of the process and is never reclaimed, even for flags that were deleted long ago, though the practical size stays negligible.

- **Cache keys are built with `JSON.stringify([flagKey, userId])`, not a hand-picked delimiter joining the two strings.** `userId` is an unrestricted, opaque external id with no charset constraint, so a delimiter-based join (even something as unlikely as a null byte) could let two distinct (flag, user) pairs serialize to the same string, aliasing one cache entry onto the other. JSON's escaping guarantees this cannot happen regardless of what either string contains.
  Consequences: slightly more CPU per cache key than a plain string join, and cache keys are no longer human-readable at a glance in logs.

- **`flagService`, `overrideService`, and `evaluationService` are factories (`createXService(deps)`), not static function modules**, each taking their repository and cache dependencies explicitly, with one composition point (`src/container.ts`) wiring a single real cache instance and the real repositories for the running app. This is a larger change than the cache itself: it was needed so evaluation-cache tests can construct a fully isolated cache and mock repository per test rather than sharing global mutable state, while `flagService`/`overrideService` still needed to reach that same cache instance to invalidate it on writes. Existing Stage A integration tests kept working unmodified because they exercise the real HTTP app, and `jest.spyOn` on the repository module still intercepts calls made through it regardless of which service factory holds the reference.
  Consequences: there is now one more file, `src/container.ts`, that has to be updated whenever a new service or a new shared dependency is added, and the wiring between services is implicit there rather than each service importing exactly what it needs.

- **Cache TTL and max size come from zod-validated environment config** (`CACHE_TTL_MS`, `CACHE_MAX_ENTRIES`, both with sane defaults), extending `src/config/env.ts` from a plain object into a validated schema. `DATABASE_URL` becoming a required field (rather than silently defaulting to an empty string) is a small side effect of the same change: it now fails fast at startup with a clear message instead of failing later, opaquely, inside Prisma.
  Consequences: the process now refuses to start at all if `DATABASE_URL` is missing, instead of starting up and failing later on the first request that touches the database.

- **`prisma` moved from `devDependencies` to `dependencies`, and the build script now runs `prisma generate` explicitly** rather than relying on `@prisma/client`'s own postinstall to do it implicitly. Confirmed directly in this environment, not assumed: `npm install` here still shows the prisma packages' lifecycle scripts as blocked ("install-scripts not yet covered by allowScripts") even after the move, meaning our own local setup had only ever worked because `prisma migrate dev` was run manually, never through automatic postinstall generation. If a build environment (this project's own, or DigitalOcean's Node buildpack) prunes `devDependencies` or blocks install scripts, an implicit-generation approach silently degrades to a stale or missing client. An explicit `prisma generate` step in the build script removes that dependency on install-script behavior entirely.
  Consequences: `prisma`, a much larger package than just the client, is now installed in every environment including production, not only where builds happen.

- **Prisma's connection_limit is set in application code** (`src/db/prisma.ts`, via `URL`/`URLSearchParams` on the resolved `DATABASE_URL`), not by string-concatenating a query parameter onto the platform-bound `${db.DATABASE_URL}` value in `.do/app.yaml`. The bound value's exact format (whether it already has query params such as `sslmode`) is only known at deploy time, so blindly appending `?connection_limit=N` risks producing a malformed URL (a second `?` instead of `&`). `URLSearchParams.set` adds or overwrites the single param correctly regardless of what else is already in the URL. Chose a limit of 5 per instance: DigitalOcean's documented limit for the smallest general-purpose managed Postgres plan (1 GiB RAM) is 22 backend connections; the Dev Database tier's exact underlying spec is not published, so this is the closest verified reference, not a confirmed match. 5 per instance leaves headroom for the PRE_DEPLOY migration job's own connections, for scaling `instance_count` up later, and for ad hoc admin connections, without materially affecting an API whose evaluate path is served mostly from cache. Configurable via `DATABASE_CONNECTION_LIMIT`.
  Consequences: the actual per-instance connection limit is invisible from `.do/app.yaml` alone; someone auditing the deployment config would need to also read `src/db/prisma.ts` to find it.

- **Node version pinned to 20 via `.nvmrc`**, read by CI's `setup-node` step via `node-version-file`. No version was pinned anywhere before this (no `.nvmrc`, no `engines` field), even though the local sandbox actually runs Node 24. Chose 20 because it matches the `@types/node` major version already in `package.json` (`^20.14.9`), keeping local types and the CI runtime consistent, rather than matching whatever this particular sandbox happens to run.
  Consequences: CI and any future contributor need Node 20 available specifically, and this pin will not track newer LTS releases until someone deliberately bumps it.

- **Added a global Jest test guard that refuses to run any test unless `DATABASE_URL` contains `flags_test`.** No such guard existed before this: tests ran against whatever `DATABASE_URL` was set, with nothing stopping the integration suite's real DELETEs from hitting a non-test database. This required setting up a dedicated local `flags_test` database and a committed `.env.test` (no secrets, just a local connection string), separate from the `feature_flags` database used for manual dev testing, since the local dev database's name does not contain `flags_test` and would otherwise now fail the guard. `tests/globalSetup.ts` loads `.env.test` via dotenv before checking, but only fills in values not already set, so it is a no-op in CI, where the workflow sets `DATABASE_URL` directly as a job-level env var.
  Consequences: local `npm test` now requires a second, separate local database to exist before any test can run at all, which is documented in the README but is one more manual setup step than a single shared database would have needed.
